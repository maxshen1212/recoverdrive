# RecoverDrive Phases 1–4 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task (this run is native/inline under the autonomous-run skill). Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build the full detect → diagnose → recover → verify → fallback pipeline on nuScenes-mini with baselines B0–B3, run E1/E2 on dev then once on the frozen test split, and run E3 closed-loop in CARLA 0.9.16.

**Architecture:** Deterministic checks (Python) + Qwen3-VL judgment (vLLM, schema-constrained JSON), behind one cached VLM client. One evaluation runner iterates (scene × fault × seed) runs in parallel threads; each frame computes shared perception/checks once and feeds every method, so methods differ only in diagnosis/recovery. A SQLite cache keyed on request content makes SAM 3 and VLM work reusable across methods, seeds and reruns.

**Tech Stack:** Python 3.12 / uv, numpy, nuscenes-devkit, transformers `Sam3Model`, OpenAI client → vLLM 0.32 (Qwen3-VL-8B-Instruct), sqlite3, pytest, ruff, CARLA 0.9.16 (+ `carla` 0.9.16 cp312 wheel).

**Spec:** `docs/superpowers/specs/2026-11-03-recoverdrive-design.md`

## Global Constraints

- Split: 6 dev / 4 test scenes in `configs/splits.yaml`. Tune prompts and thresholds on dev only; run test once after freezing (spec §5.4).
- Stochastic settings: 3 seeds, report mean ± std (spec §5.4).
- Initial check values: k = 5 points, IoU ≥ 0.3, range 50 m; calibrate on dev, then fix (spec §4.1).
- Recovery: re-ask ≤ 2 on bad format; on suspected fault sample 3× at temperature 0.7, majority vote, agreement = confidence (spec §4.3).
- Shield is rule-based, no LLM; actions ordered continue < slow_down < stop; TTC brake at 2 s in CARLA (spec §4.5).
- All methods use the same Qwen3-VL-8B, data and faults; B1–B3 feed the same shield (spec §5.1).
- C1 and L4 have no severity and count as high (spec §5.2). ~50% of frames clean; episodes ≥ 2 frames; seeded (spec §3.3).
- Never add `vllm` to the root `pyproject.toml`. `source scripts/env.sh` in every shell. Pin GPUs with `CUDA_VISIBLE_DEVICES`.
- CARLA: 0.9.x, `-RenderOffScreen`, installed on the data disk outside the repo, no sudo.

## Review Focus

1. Frames where no GT box projects into a camera (night scenes, empty roads): `match_rate` is `None`; flags and metrics must not treat this as a fault or crash. Test: `test_flags_skip_camera_without_reference` (T1).
2. Empty or near-empty LiDAR cloud (L4, L1 high): sector counts, BEV render and agreement must work on 0 points. Test: `test_lidar_health_empty_cloud` (T1), `test_render_bev_empty` (T3).
3. VLM server returns non-JSON, times out, or the HTTP call raises: a run must record an invalid attempt, never kill the run. Test: `test_caller_records_exception_as_invalid` (T3).
4. Reruns after a crash: finished run files are skipped, partial ones redone; cache hits return identical results. Test: `test_runner_resumes_completed_runs` (T4).
5. Accidental test-split use before freezing: the runner must refuse `--split test` unless the config says `frozen: true` and the git tree is clean. Test: `test_runner_refuses_unfrozen_test` (T4).

## Decisions taken as defaults (not settled by the spec)

- **DEFAULT (D1)** Monitor all 6 nuScenes cameras + LiDAR. The VLM sees a labeled 3×2 mosaic of the current frame, the previous-frame mosaic and a LiDAR BEV (3 images; `serve_vlm.sh` limit raised to 3).
- **DEFAULT (D2)** Methods without recovery (B1–B3, Ours-detect): status `ok` → `healthy`; `fault`/`uncertain`/invalid → `unresolved` (stop). Recovery success is N/A for them.
- **DEFAULT (D3)** E1 positive = method's final state ≠ healthy (for Ours-detect/baselines: status ≠ ok, invalid included). Sensor accuracy is over true-positive frames; agent faults count as sensor `agent`.
- **DEFAULT (D4)** Agent-fault severity = number of corrupted diagnosis attempts in the frame: low 1, medium 2, high 3. A2 flips the verdict (ok ↔ fault); A3 raises a simulated timeout without waiting.
- **DEFAULT (D5)** Severity parameters: L1 {random drop 0.3/0.6/0.9, beam drop 25/50/75 % of 32 elevation bins, sector 45/90/180°}; C2 {rotate 2/5/10°, shift 3/8/15 %}; C3 {blur σ 2/5/10, noise σ 10/30/60, overexpose ×1.5/2.5/4, black = high}; C4 {lag 1 frame / lag 2 frames / full freeze}; L2 {0.1 m+0.5°, 0.3 m+2°, 1.0 m+5°}. C2–C4 target CAM_FRONT with p = 0.5, else one of the other 5 cameras uniformly.
- **DEFAULT (D6)** Re-observation is causal: a sensor suspected at t−1 and t is "persistent"; an isolated sensor is restored after one frame with no flag and no VLM blame. A new suspicion isolates at once if vote confidence ≥ τ = 0.6.
- **DEFAULT (D7)** "Front perception available" = CAM_FRONT or LiDAR not isolated.
- **DEFAULT (D8)** L3 (ghost points) is not run in E1/E2: the GT-box LiDAR detector cannot see it by construction (spec §8.2).
- **DEFAULT (D9)** B1–B3: Qwen captions each camera (cached, T = 0); LiDAR objects become DriveAgent-style text (class, x/y in ego frame, points); one schema-constrained call per frame: zero-shot (B1), CoT with a `reasoning` field first (B2), single-call Self-Refine with `initial`/`critique`/`refined` fields first (B3), mirroring DriveAgent's `vehicle_prompts.json` (github.com/Paparare/DriveAgent).
- **DEFAULT (D10)** Dev runs for calibration use seed 0 only; the test run uses seeds 0, 1, 2.
- **DEFAULT (D11)** E3: ego follows the route with Traffic Manager autopilot set to ignore vehicles and walkers; every method (B0 included) keeps the vehicle's own camera-based TTC < 2 s brake. When CAM_FRONT is isolated, the TTC brake switches to LiDAR objects. Monitor runs at 2 Hz. Faults in E3: none and C1.
